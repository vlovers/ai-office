# v0.5 review-feedback threat model

Trust boundary: a single trusted local OS user authorizes a bounded Codex write turn in an
existing isolated worktree. Repository data, filenames, diffs and agent text are untrusted.
Local host administrators/processes, repository Git configuration and operator-selected
host verification commands retain the v0.4 assumptions. This does not provide complete
isolation against the OS user, arbitrary host commands or detached processes.

| Surface / threat                                                        | Control and remaining boundary                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Filename traversal, wildcard/magic pathspecs, HTML/script content       | Backend Git retains literal paths and disabled hooks, filters, external diff/textconv and submodule inspection. Untracked reads retain canonical/no-follow identity checks and size limits. Comment paths must exactly match persisted review entries. React text nodes render filenames, source and feedback; no HTML evaluation, webview, Markdown execution or source execution is used.                                                                              |
| Sensitive or undisplayable changes hidden from decisions                | Every returned changed file retains an explicit availability status. Sensitive content is withheld before persistence. Binary, oversized, unavailable and budget-exhausted files stay in the explorer. Over 500 files is a visible error requiring local inspection. Filtering is user-controlled and reports visible/total counts. Existing sensitive-path filtering is defense in depth, not a complete secret scanner.                                                |
| Stale revisions and relocated line comments                             | Review artifacts have an exact revision hash plus monotonic workspace-local display number. Old/new anchors must occur in the persisted patch. Comments never migrate to another revision; historical anchors are labeled outdated. Request/Keep/Reject/Verify require a fresh revision under existing leases. External editors remain outside the lease; metadata observations are not atomic filesystem snapshots.                                                     |
| Feedback edited after confirmation, duplicate requests, concurrent tabs | Draft versions reject conflicting saves. Submitted feedback is immutable. Request Changes sends only persisted feedback. Exact workspace/revision is the idempotency key: a duplicate returns its original continuation, without another model call. Conflicting concurrent operations fail busy; task, queue and submitted history commit in one SQLite transaction. A lost HTTP response can be retried safely.                                                        |
| Worktree replacement, branch/base advancement, write escalation         | Existing authorization roots, canonical Git/common directories, device/inode/birth-time fingerprints and pending decision are revalidated. A request cannot select another session, executable, permission mode, root or prompt. It submits a write task to the original fixed agent/provider and saved session. Execution rechecks workspace and revision after asynchronous auth before executeTask. Kept/rejected workspaces cannot continue.                         |
| Wrong/missing native session, interrupted resume                        | SDK resumeThread is used with the original ID and compatible binding; no startThread fallback is added. Different resumed thread events fail and trigger supervised cleanup. Missing/incompatible native state produces the provider's sanitized failure. The SDK loads native transcripts; no guaranteed recovery or preflight proof of transcript availability is claimed. Native transcript access/availability is not inferred by reading authentication files.      |
| Crash during submission or execution                                    | Schema 6 migrates transactionally. Submission atomically records the existing-queue task and immutable feedback relation. Queued, explicitly confirmed work retains the existing queue restart semantics. Active tasks recover as interrupted, without auto retry; their review generation advances. Worker cleanup/lease uncertainty retains v0.4 fail-closed behavior. History survives Keep/Reject and restarts. Filesystem and SQLite are not an atomic transaction. |
| Stale verification used as proof of corrections                         | Verification results are bound to their input review revision and shown as earlier when it changes. Host verification remains disabled by default, separately operator-enabled and explicitly confirmed. It executes project scripts with host privileges, including AI edits; no arbitrary HTTP executable is accepted and no sandbox guarantee is implied.                                                                                                             |
| Resource exhaustion and persistent sensitive text                       | Existing Git process time/output and ownership-scan bounds remain. Patches are capped per file and globally; rendering uses 200 rows and truncated display lines; history responses use 20-record pages. Feedback body/count/total size is bounded. SQLite retains review artifacts without a quota/encryption/retention policy. User-authored secrets can still be persisted; do not include secrets in comments.                                                       |

Validation uses disposable Git repositories/databases, the real pinned SDK with a synthetic
CLI transport, production browser UI and native sandbox probes, without model calls. New
coverage exercises stale/duplicate/concurrent requests, queue crash consistency, invalid
paths/anchors, sensitive/binary/large files, provider failure, thread preservation, stop,
verification attribution and restart. Existing v0.4 adversarial tests continue to cover
worktree replacement, advanced HEAD, ignored/nested data preservation, filters, literal
pathspecs, subprocess cleanup and unauthorized filesystem access. See
[V0_5_VALIDATION.md](V0_5_VALIDATION.md) for exact results and the inherited
[v0.4 audit](V0_4_SECURITY_AUDIT.md) for the original findings and remaining boundaries.

The follow-up [focused PR #9 audit](V0_5_SECURITY_AUDIT.md) records confirmed cancellation and unsaved-draft recovery defects, their fixes and final validation evidence.
